# Feature Specification: Gacha Spend Tracker

**Feature Branch**: `001-gacha-spend-tracker`

**Created**: 2026-11-25

**Status**: Draft

**Input**: User description: "开发抽卡与氪金记录网站：覆盖原神、星穹铁道、绝区零、恋与深空、无限暖暖；按游戏分界面；显眼展示目标物品所需抽数/花费/氪金方案（含礼包、首充双倍、累充）；支持 0 抽 0 氪或自填进度；注册登录保存数据；纯文字但预留图片与立绘接口；技术栈 Next.js + MySQL + Docker。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 目标花费计算器（Priority: P1）

玩家打开某一游戏页面，选择目标（单推 / all 推 / 满命或满精或整套服装等），可从 0 抽 0 氪开始，或填写当前保底进度、已拥有份数、已用双倍档位、库存抽数等；页面首屏显著展示：还差多少抽、期望与最坏花费区间、推荐氪金购买组合。

**Why this priority**: 用户明确这是主功能，必须显眼且可用。

**Independent Test**: 不登录也能完成一次计算并看到方案；用固定输入可复现抽数与花费数字。

**Acceptance Scenarios**:

1. **Given** 原神角色池 0 抽且无大保底，**When** 目标为「1 个当期 UP 角色」，**Then** 展示小保底 90 / 大保底 180 的最坏抽数，以及对应期望说明与花费估算。
2. **Given** 玩家已垫 70 抽且处于大保底，**When** 目标为 1 个 UP 角色，**Then** 所需抽数按剩余保底计算（最多 20），花费相应减少。
3. **Given** 勾选可用首充双倍与月卡选项，**When** 生成氪金方案，**Then** 方案列出具体商品组合与总人民币，并说明是否动用双倍档。

---

### User Story 2 - 按游戏分区浏览与规则数据（Priority: P1）

玩家从首页进入五个游戏之一，看到该游戏的计算器、进度输入、以及文字列表形式的可抽目标（角色 / 武器或光锥音擎 / 思念 / 服装套装）。列表项预留图片字段但不强制显示图。

**Why this priority**: 五游戏是产品范围硬边界；无数据则计算器无意义。

**Independent Test**: 每个游戏路由可打开，且至少能选一类目标完成计算。

**Acceptance Scenarios**:

1. **Given** 首页，**When** 点击任一游戏，**Then** 进入该游戏独立界面且导航可返回。
2. **Given** 某游戏界面，**When** 浏览目标列表，**Then** 纯文字可读，数据结构含 `imageUrl` 可空字段。

---

### User Story 3 - 注册登录与进度保存（Priority: P2）

玩家注册账号并登录后，可将各游戏的保底进度、已购双倍档位、库存抽数等保存到账户；下次登录自动回填计算器。

**Why this priority**: 用户要求账户记录；但无登录时计算器仍应可用。

**Independent Test**: 注册 → 登录 → 保存进度 → 退出再登录 → 数据仍在。

**Acceptance Scenarios**:

1. **Given** 未登录用户，**When** 完成计算，**Then** 结果可用且提示登录可保存。
2. **Given** 已登录用户修改进度并保存，**When** 重新打开该游戏页，**Then** 表单回填上次保存值。

---

### User Story 4 - 背景立绘接口（Priority: P3）

每个游戏页面与目标详情预留背景 / 立绘 URL 接口；首版可不配置素材，配置后可显示而不改布局逻辑。

**Why this priority**: 用户明确后续美化，首版不插图。

**Independent Test**: 字段存在；空值时布局正常；填入 URL 时渲染容器可显示。

**Acceptance Scenarios**:

1. **Given** `bgArtUrl` 为空，**When** 打开游戏页，**Then** 无破图、布局完整。
2. **Given** 配置了有效 `bgArtUrl`，**When** 打开游戏页，**Then** 背景区域使用该资源。

---

### Edge Cases

- 目标份数超过游戏上限（如超过满命）时拒绝并提示合法范围。
- 无限暖暖未集齐前按保新计算；海风的祝颂是否已用影响最坏抽数。
- 原神武器定轨命定值、恋与深空多人池定向值在换池时不跨期继承，计算器须区分「跨期继承」与「当期清空」字段。
- 累充活动规则因版本变化大：首版以用户手填「累充门槛奖励抽数」或开关参与；无活动时默认关闭。
- 密码错误 / 重复用户名给出明确错误，不泄露其他账户信息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供五个游戏独立页面：原神、崩坏：星穹铁道、绝区零、恋与深空、无限暖暖。
- **FR-002**: 系统 MUST 在游戏页首屏显眼位置展示「目标 → 抽数 → 花费 → 氪金方案」计算结果。
- **FR-003**: 系统 MUST 支持从 0 抽 0 氪起算，也支持玩家输入已垫抽数、是否大保底、定轨/定向进度、已拥有目标份数、库存抽数/货币、已用首充双倍档位。
- **FR-004**: 系统 MUST 按各游戏机制计算单推、多目标（all 推）及满命/满精/整套等标准目标的最坏抽数；在概率规则可建模时给出期望抽数，并标明假设。
- **FR-005**: 系统 MUST 根据所需抽数生成氪金方案，考虑直充档位、首充双倍、小月卡、大月卡/纪行类、常见礼包性价比，以及可选的限时累充输入。
- **FR-006**: 系统 MUST 将各游戏抽卡机制、商品表、可抽实体写入数据库并可种子初始化。
- **FR-007**: 系统 MUST 提供邮箱或用户名 + 密码的注册登录，并保存每用户每游戏进度。
- **FR-008**: 实体与游戏页 MUST 预留 `imageUrl`、`bgArtUrl`（可空）；首版 UI 为纯文字。
- **FR-009**: 系统 MUST 可用 Docker Compose 启动应用与 MySQL。
- **FR-010**: 计算器对无法精确建模的软保底曲线，MUST 明确采用「硬保底规划」或注明期望为近似，不得伪装为官方精确公式。

### Key Entities

- **Game**: 游戏标识、显示名、背景立绘 URL、机制配置引用。
- **GachaPoolType**: 池类型（角色/武器/思念/服装等）及保底参数。
- **PullableItem**: 可抽目标（角色、武器、思念、服装套装/部件），含稀有度、满阶定义、图片 URL。
- **ShopOffer**: 氪金商品（价格人民币、获得抽数或货币、限购、是否双倍档、礼包类型）。
- **User**: 账户凭证。
- **UserGameProgress**: 用户在某游戏的保底与氪金状态快照。
- **CalcResult**: 抽数需求、花费区间、推荐购买清单（可计算生成，未必持久化）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在 2 分钟内可完成「选游戏 → 设目标 → 看到抽数与花费方案」。
- **SC-002**: 对每个游戏至少 3 组固定输入样例，最坏抽数与人工按硬保底推算一致。
- **SC-003**: `docker compose up` 后本地可访问站点并完成注册、计算、保存进度闭环。
- **SC-004**: 未配置任何图片 URL 时五个游戏页均可正常使用；配置后无需改代码即可显示。

## Assumptions

- 认证采用用户名/邮箱 + 密码（会话 Cookie）；不做第三方 OAuth（首版）。
- 首版期望计算：硬保底路径为主展示；软保底期望可用简化模型或标注「规划用最坏值」。
- 累充活动不内置全部历史活动表，提供通用「累充奖励」输入项。
- 角色/服装种子数据覆盖主流可抽目标即可，不必一次穷尽全图鉴；结构支持后续追加。
- 人民币档位以国服常见标价为准（6/30/68/98/128/198/328/648 等按游戏实际商品表配置）。
- 捕获明光等低概率「纠偏」机制：最坏路径按不触发计算；期望路径可按社区综合 UP 率（如约 55%）可选开关。
